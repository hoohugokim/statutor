# Specification: v0.4 portable user layer

## Decision and scope

A global layer is appropriate because cross-repository working agreements and
reusable skills are user-scoped by every supported host, while today they are
copied and drift independently. It is not another project ledger. It is an
opt-in projection manager around human-owned global instruction/skill sources.

This specification is accepted by D-0018. Its ownership model keeps the core
doctrine intact: one writer per file. Humans edit canonical sources and host
overlays; Statutor owns complete generated target files/directories only after
explicit apply or adoption. Managed blocks inside otherwise human-owned files
are out of scope.

Implementation status (2026-08-31): the v0.4 agent-side scope is complete.
`statutor_global` provides explicit-root resolution, strict versioned config /
state / artifact schemas, safe deterministic tree hashing, a state lock and
journals, durable compare-and-swap file/tree replacement, exact backups, and
restore primitives. No real home was touched.
The instruction lifecycle is also complete: init/plan/adopt/apply/status/
uninstall are exposed through the packaged CLI; whole-file projections,
pre-displayed plans, original-byte adoption, CAS refusal, rollback, and
precedence warnings are covered under fake homes. The skill lifecycle is now
complete too: local new-only import, core Agent Skills validation, exact-tree
portable and Claude projections, foreign-lock coexistence, duplicate
classification, explicit identical adoption, source-to-target sync, receipts,
journals, rollback, and safe uninstall are covered under fake homes and the
installed-wheel smoke gate. Unified status/doctor is complete: stable JSON and
human output explain effective instruction precedence, ownership/drift,
foreign/disabled/legacy/native/admin/plugin skill roots, active duplicate
conflicts, unsafe links, receipt/realpath integrity, and explicit instruction
and skill-description budgets. Fast status is metadata-first; deep doctor
performs full-tree validation without invoking a host or network. The opt-in
fake-profile E2E pins the three local host baselines, verifies every projection
on disk, exercises Codex's assembled prompt and OpenCode's resolved skill
inventory, and records Claude's lack of an equivalent offline personal-skill
inventory without claiming stronger native evidence. Modified-target refusal
and exact uninstall recovery pass; the caller's real home remains untouched.

## Evidence and host contract

The host matrix is grounded in current primary documentation:

- [Claude Code memory](https://code.claude.com/docs/en/memory) loads global
  `${CLAUDE_CONFIG_DIR:-~/.claude}/CLAUDE.md`; [Claude Code skills](https://code.claude.com/docs/en/slash-commands)
  load `${CLAUDE_CONFIG_DIR:-~/.claude}/skills/<name>/SKILL.md`, support
  symlinks/live detection, and give enterprise > personal > project precedence.
- [Codex AGENTS discovery](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
  uses the first non-empty `$CODEX_HOME/AGENTS.override.md`, otherwise
  `$CODEX_HOME/AGENTS.md`; an override shadows the base, and the default
  combined project-instruction budget is 32 KiB. [Codex skills](https://learn.chatgpt.com/docs/build-skills)
  document `$HOME/.agents/skills` for user scope; same-name skills remain
  distinct rather than being merged.
- [OpenCode rules](https://opencode.ai/docs/rules/) use
  `$XDG_CONFIG_HOME/opencode/AGENTS.md`, falling back to
  `~/.claude/CLAUDE.md` only when native global AGENTS is absent. [OpenCode skills](https://opencode.ai/docs/skills/)
  discover native, `.claude/skills`, and `.agents/skills` roots.
- Every portable skill must satisfy the [Agent Skills specification](https://agentskills.io/specification)
  without stripping host-specific frontmatter extensions.

Local evidence makes no-clobber behavior mandatory: Claude and Codex already
have divergent hand-authored global instruction files; OpenCode currently
inherits Claude because its native AGENTS is absent; Claude's skills root is a
symlink; a foreign `~/.agents/.skill-lock.json` owns three skills; and eleven
other skills are byte-identical triplicates across Claude, legacy Codex, and
native OpenCode roots.

The verification baselines are Claude Code 2.1.251, Codex CLI 0.151.0, and
OpenCode 1.18.20 on 2026-08-31. They scope tested contracts, not minimum-version
promises. v0.4 targets Claude Code, Codex, and stable OpenCode v1; it inventories
OpenCode v2 as unsupported until its changed discovery semantics receive their
own decision and E2E profile. Admin/enterprise policy always outranks and
remains outside Statutor ownership.

## Files and writers

Defaults are overridable by explicit `--home`, `--config-root`, and
`--state-root` arguments, never by mutating process-wide home variables:

| Artifact | Default | Writer |
|---|---|---|
| Common global constitution | `$XDG_CONFIG_HOME/statutor/AGENTS.md` | human |
| Host overlays | `$XDG_CONFIG_HOME/statutor/hosts/{claude,codex,opencode}.md` | human |
| Human config | `$XDG_CONFIG_HOME/statutor/global.json` | human |
| Canonical skill sources | `$XDG_CONFIG_HOME/statutor/skills/<name>/` | human after explicit local import |
| Portable skill projections | `$HOME/.agents/skills/<name>/` | statutor global per receipt, unless foreign-managed |
| Claude skill projections | `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/skills/<name>/` | statutor global per receipt |
| Projection receipt | `$XDG_STATE_HOME/statutor/global-state.json` | statutor global |
| Backups | `$XDG_STATE_HOME/statutor/backups/<operation-id>/` | statutor global |
| Host instruction projections | native global instruction paths | statutor global after adoption |

On POSIX, the Statutor config/state fallbacks are `~/.config/statutor` and
`~/.local/state/statutor`; `XDG_CONFIG_HOME` and `XDG_STATE_HOME` take
precedence. On Windows they are `%APPDATA%/statutor` and
`%LOCALAPPDATA%/statutor/state`. Host roots independently honor their documented
`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, and `XDG_CONFIG_HOME` contracts. Config and
receipts are versioned JSON so the zero-dependency Python kernel never requires PyYAML.
Receipts store source/target canonical paths, host/version, kind, ownership,
deterministic tree or content digest, last-installed digest, backup ID, and
effective discovery topology. Timestamps are informational, never identity.

## Instruction lifecycle

The v0.4 command surface is `statutor global {init,plan,adopt,apply,status,
doctor,uninstall,restore}` and `statutor global skill {import,status,plan,apply,
sync,uninstall}`. Planning/status are read-only; every mutating command supports
the same explicit root overrides used by tests.

1. `statutor global init` scaffolds only the Statutor config, common AGENTS,
   and empty overlays when absent. It performs no host mutation.
2. `statutor global plan` resolves host homes and effective precedence, then
   prints exact creates/replacements, shadowing, conflicts, and backups. It is
   read-only and supports stable `--json`.
3. An absent target may be created by explicit `apply`. An existing unmanaged
   target is always a conflict; there is no generic `--force`.
4. `statutor global adopt HOST` first backs up the complete existing file,
   imports its body verbatim into that host's overlay, and shows the complete
   first projection before ownership changes. The old body must remain
   byte-for-byte present. A nonempty common source is an explicit addition, so
   the command must report that behavior may change rather than claim semantic
   equivalence.
5. A projection is deterministic: generated header + common source + named
   host overlay. Users edit the sources, never the projection.
6. Codex `AGENTS.override.md` is never a target. If present, status reports the
   managed base as shadowed and apply refuses to claim it is effective.
7. Creating native OpenCode AGENTS changes precedence by suppressing Claude's
   fallback; plan calls this out and requires explicit host selection.
8. `sync` uses compare-and-swap: update only when the current target digest
   equals the receipt. A human-edited projection is `modified` and is never
   overwritten. `uninstall` has the same rule; `--forget` drops only receipt
   ownership and leaves the artifact. `restore BACKUP_ID` is explicit.

### Constitution content contract

`init` creates a commented scaffold, not invented preferences. The common
constitution may contain only cross-project working agreements: instruction
precedence, shared-worktree care, bounded delegation and file ownership,
evidence-based handoff, verification expectations, and approval/safety
boundaries. A useful multi-agent rule tells the delegator to pass relevant
project constraints and an explicit file scope to each worker, then reconcile
their evidence before declaring completion. It cannot assume that every host
automatically gives subagents the same context.

The common constitution is behavioral guidance, never an enforcement claim.
It has Statutor's 120-line soft/200-line hard discipline, must not contain
secrets, project commands, machine-specific paths, or a requirement that every
repo adopt Statutor, and yields to closer project instructions. Host syntax and
host-only behavior belong in overlays. Doctor also enforces Codex's configured
combined instruction byte budget.

## Skill lifecycle

Canonical sources live under Statutor's config root and remain human-editable.
Statutor projects them to the documented common user location for Codex and
OpenCode and to Claude's personal location. Because OpenCode discovers both
`.agents` and `.claude` roots, duplicate-identical projections are expected and
must be proven harmless on the supported release; divergent duplicates are a
hard conflict. Do not create a third native OpenCode copy by default.

- `skill status [--json]` inventories portable, Claude, native OpenCode,
  legacy `$CODEX_HOME/skills`, plugin/synced/admin-visible names, and the
  foreign lock without writing any of them.
- `skill import PATH` accepts local sources only in v0.4. It validates the core
  SKILL.md name/description/directory contract, preserves extensions, rejects
  special files plus escaping/cyclic links, hashes the complete tree, and
  copies it only to a new canonical source. Re-import never overwrites an
  existing source. A separate plan/apply creates portable + Claude targets.
- Existing absent targets may be atomically materialized. Identical unmanaged
  targets require `--adopt-identical`; differing targets are conflicts. A name
  present in a foreign lock is `foreign-managed`: Statutor inventories it but
  never adopts, updates, removes, projects over, or edits its lock entry.
- `skill sync` is strictly source→targets and compare-and-swap guarded. There
  is no bidirectional merge. `skill uninstall` removes only unchanged targets
  recorded as Statutor-owned and removes parent directories only when empty
  and created by the same receipt.
- Source acquisition, Git pulls, registries, auto-update, Codex's installer,
  Claude plugins/marketplaces, and OpenCode package management remain their
  owners' jobs. Statutor manages visibility and drift, not supply chain.

## Status and doctor

`global status` is read-only and exits 0 when inventory succeeds. Human output
and stable JSON report host versions, effective instruction source, managed /
unmanaged / foreign-managed ownership, installed / missing / outdated /
modified / shadowed / disabled state, and identical/divergent duplicates.

`global doctor` performs the deep deterministic audit. Warnings keep exit 0;
errors exit 1. It validates config/receipt schemas, source and target digests,
generated headers, precedence and overrides, disabled compatibility roots,
skill manifests, logical-name and realpath collisions, broken/escaping/cyclic
links, plugin/admin/synced conflicts, and the initial skill-description budget.
Default doctor performs no network/model call. Optional `--probe` may invoke
host-native discovery diagnostics because those commands can write logs/state.

## Mutation safety

- Every mutation is preceded by the same resolved plan shown to the user.
- Write a same-directory temporary file/tree, flush, preserve safe permissions,
  and rename into place; do not follow an existing target-entry symlink for
  overwrite. An explicitly adopted container-root symlink is allowed only after
  recording and validating both its logical path and contained real path.
- Serialize Statutor operations with a state-root lock and durable operation
  journal. This does not pretend that unrelated host filesystems form one
  atomic transaction.
- Re-read every target immediately before rename and compare its planned
  precondition digest. Concurrent change aborts the remaining operation.
- Back up before replacing or adopting anything; never auto-expire backups in
  v0.4. Partial failure rolls back an earlier target only if it still matches
  the just-installed digest; otherwise it leaves both artifact and evidence for
  explicit recovery. The journal reports the exact mixed state.
- Never touch admin/enterprise/system, plugin cache, account-synced, host
  JSON/TOML, or foreign lock files. Never mutate the real home in tests.

## Verification matrix

Unit/integration tests use explicit fake config/home roots and cover:

- empty init, idempotent plan/apply, unmanaged collision, explicit adoption,
  source drift, target hand-edit, concurrent change, uninstall, forget, restore;
- Codex override shadowing and byte cap; OpenCode native-vs-Claude fallback;
  Claude config-dir override and a skills root that is itself a symlink;
- valid/invalid skills, same-name identical/divergent trees, foreign locks,
  special files, broken links, escaping links, cycles, and description budget;
- stable JSON schemas, deterministic ordering/hashes, permissions/newlines,
  injected write failures, and rollback.

Real-release E2E is a separate, explicit test profile. It proves exact generated
instruction and skill projections for every host, then uses the native offline
discovery surfaces available in the pinned releases: Codex's assembled prompt
contains the instruction and one skill catalog entry, and OpenCode resolves the
portable/Claude duplicate to one skill entry. Claude 2.1.251 exposes no
equivalent offline personal-skill inventory, so its projection is verified on
disk and that limitation is reported. The profile also proves modified-target
refusal and uninstall recovery. Dogfooding onto the maintainer's actual home is
a distinct user-approved operation after fake-home tests and a reviewed plan;
this roadmap does not authorize it.

## Done means

- One common instruction edit and one skill edit produce deterministic,
  inspectable updates across supported hosts without losing existing content.
- A fresh status explains which instruction/skill each host will actually use,
  including shadowing and foreign ownership.
- Re-running apply is a no-op; hand edits and concurrency cause refusal, not
  overwrite; uninstall removes only unchanged Statutor-owned projections.
- The existing divergent global files and triplicated skills can be presented
  as a reversible migration plan, but remain untouched until separately
  approved.

## Non-goals

Enterprise/admin deployment; cloud/Cowork/account-synced lifecycle; plugin or
marketplace lifecycle; remote installation/update; daemon/watch mode; global
enforcement hooks; bidirectional merge; host config rewrites; automatic home
migration/deletion; OpenCode v2 before stable; and any attempt to make global
instructions override project-local constitutions.
